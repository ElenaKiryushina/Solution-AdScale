**Проектирование взаимодействия микросервисов ADScale.**

**Внутреннее взаимодействие**

*   **Синхронное взаимодействие - gRPC (для критичного пути).** Критичный путь – это процесс максимально быстрой (за миллисекунды) выдачи баннера-победителя в ответ на запрос DSP-площадки (вне зависимости от того на сколько шагов, выполняемых разными микросервисами этот процесс поделен внутри). Используется между API Gateway, Ad Server, RTB Service и Delivery Serviсe (**API Gateway $\to$ AD Service $\to$ RTB Service $\to$ Delivery Service**). Обеспечивает минимальную задержку и высокую скорость передачи данных (в отличии от текстовые форматов REST требующих доп.обработки), рекомендуется для взаимодействия между сервисами на разных языках.
    
*   **Синхронное взаимодействие –** **REST/ gRPC –** возможны оба протокола при маршрутизации от API Gateway к внутренним сервисам.
    
*   **Асинхронное взаимодействие (Kafka):** Используется для публикации событий по показам и кликам из сервиса Delivery Service в сервисы Analytics Service, Financial Service, которые просто подписаны на эти очереди сообщений. Этот подход позволяет сервисам работать независимо и отказоустойчиво, балансируя нагрузку на БД.
    
**Внешнее взаимодействие**
**API Gateway** - выступает единой точкой входа для внешних запросов (от WEB UI, DSP-партнера). Протоколы на входе: HTTPS /REST от WEB UI, HTTPS/OpenRTB от DSP-партнера.
API Gateway необходим в первую очередь для обеспечения стандартизированного и быстрого взаимодействия с DSP-площадкой. Важен общий контроль rate limiting, единая аутентификация для всех 7 сервисов, а также, учитывая, что сервисы написаны на разных тех.стеках и для ЛК рекламодателя нужны данные нескольких сервисов, использование API Gateway выглядит обоснованным.
Для выбора конкретного API Gateway нужно учесть несколько факторов:
- поддержка протокола gRPC для внутренней коммуникации – см.критичный путь выше
- Масштабируемость - Способность обрабатывать скачки нагрузки (с 18 000 до 50 000 RPS)
- Нативное развёртывание в Kubernetes и готовые модули для Rate limiting, Circuit Breaker и логирования.

**Соответственно, учитывая ограничения бюджета и времени, рекомендуемая реализация — переход к модульному монолиту (для стабилизации) с последующим выделением наиболее критичных компонентов (через использование gRPC и Kafka) в полноценные микросервисы.**
