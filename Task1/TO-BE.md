# Предлагается постепенная эволюция архитектурного стиля ИС компании AdSсale от текущего гибридного монолита к модульному монолиту через 3 месяца и затем с использованием паттерна Strangler Fig к микросервисной архитектуре на горизонте года.

Применим Decision Matrix к AdScale:

| **Фактор** | **Значение для AdScale** |
| --- | --- |
| Команда 10–50 человек | Модульный монолит |
| Быстрый MVP через 3 месяца | Монолит / модульный монолит |
| Разные SLA для компонентов | Микросервисы/модульный монолит |
| Нет DevOps-инфраструктуры, нет выделенного SRE-инженера | Модульный монолит |
| Нет времени на полную декомпозицию | Монолит / модульный монолит |
| Разные технологии в компонентах | Микросервисы/модульный монолит |

**Почему нельзя оставить монолит?** 
Главная причина в том, что текущая архитектура не позволяет достичь целевых показателей:

* Масштабирование отдельных сервисов невозможно. Сейчас система поддерживает 15000 RPS в пике, задача поддержать 18000 RPS через 3 месяца и 50000 RPS на горизонте года. Горизонтальное масштабирование всего монолита неэффективно и ресурсозатратно.
* Требуемые SLA, надежность и время отклика. Из-за общей БД и единого процесса сервисы конкурируют за ресурсы и некритичные сервисы могут создавать блокировки для работы критичных (например, сервиса ставок) и приводить к деградации производительности. P95 latency уже сейчас превышает 100 ms.

**Почему нельзя сразу перейти на микросервисы?**

* Время. Жесткий дедлайн (через 3 месяца) делает переход нереалистичным.
* Ресурсы. Невысокий уровень DevOps-зрелости, отсутствие выделенного SRE-инженера.
* Риски бизнеса: резкая смена архитектуры создает риск остановки системы и нарушения прерывности бизнеса.

В текущих условиях наиболее реалистичным подходом на горизонте 3 месяцев для AdScale станет модульный монолит с выделением наиболее критичных компонентов – как минимум сервиса ставок и рекламного сервиса.

**Кроме того, для достижения целей на горизонте 3 месяцев необходимо:**

1. Уменьшить нагрузку на БД 
a. развернуть реплику БД, куда перенаправить тяжелые запросы на чтение аналитического сервиса 
b. убрать нагрузку на запись (прямые запросы сервиса статистики в базу) – перейдя на асинхронные сообщения через брокера.
2. Увеличить производительность и время отклика сервиса ставок: 
a. убрать синхронные вызовы в БД – для этого обеспечить кеширование (Redis) для данных, которые нужны сервису ставок (кампании, бюджет, правила ставок).

**Через 3 месяца после подключения новой DSP-площадки в первую очередь фокусируемся на:**

* выделении сервиса ставок в отдельный микросервис
* выделении сервиса статистики в отдельный микросервис с отдельной БД – снять высокую нагрузку на запись.
