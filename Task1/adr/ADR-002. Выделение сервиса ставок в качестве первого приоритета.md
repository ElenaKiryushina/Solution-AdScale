# ADR-002. Выделение сервиса ставок в качестве первого приоритета

**Дата:** 2026-11-15
**Статус:** Accepted

## Контекст

Компания AdScale планирует интеграцию с крупной DSP-площадкой, что приведет к росту количества запросов на ставки (bid requests) на 20%, а через год ожидается двукратный рост. Новый партнёр предъявляет более жёсткие SLA: стабильное время ответа не более 100 мс и штрафы за деградацию времени отклика (latency) и простои (downtime). При этом даже на текущий момент ИС AdScale находится на пределе своих возможностей — P95 времени отклика составляет 110–120 мс и наблюдаются периодические деградации в часы пик.

Сервис ставок (модуль «Аукцион») — наиболее критичный по нагрузке компонент системы и очень чувствителен к задержкам: через 3 месяца ожидается пиковая нагрузка 18 000 RPS, а через год — 50 000 RPS. Сейчас сервис ставок использует синхронные вызовы к базе данных. Текущая система — гибридный монолит (C++ / Go / Python / Node) с одним инстансом БД (PostgreSQL).

Ключевые архитектурные драйверы:

| Категория | Драйвер модуля «Аукцион» (сервиса ставок) |
| --- | --- |
| Нагрузка | 18 000 RPS в пик (через 3 месяца); 50 000 RPS в пик (через год) |

Рассматривались три альтернативы:

1. Оставить в составе единого монолита.
2. Рефакторинг в модульный монолит с изолированными границами.
3. Выделение в отдельный микросервис.

### Альтернатива 1. Единый монолит

**Плюсы:** минимальные изменения, быстрый time-to-market.

**Минусы:** нет изоляции ресурсов, при пике сервис ставок конкурирует за пул потоков и подключения к БД с другими модулями (аналитика, статистика). Нет чётких границ — риск регрессий при изменении других модулей. Кроме того, уже сейчас монолит находится на пределе возможностей.

### Альтернатива 2. Модульный монолит

**Плюсы:** чёткие границы модулей, изолированные схемы данных, публичные интерфейсы (Facades), готовность к будущему выделению в микросервис.

**Минусы:** требуется дисциплина тестирования (ArchUnit), накладные расходы на публичные интерфейсы.

### Альтернатива 3. Микросервис

**Плюсы:** независимое масштабирование, собственная БД.

**Минусы:** накладные расходы на сетевое взаимодействие, нет DevOps-инфраструктуры, нет SRE-инженера; 3 месяца — слишком мало для построения микросервисной инфраструктуры.

## Решение на горизонте 3 месяцев

Сервис ставок реализован как модульный монолит в рамках единого приложения AdScale. Применяются следующие принципы:

- Модуль имеет чёткие границы: RTB Facade как единственная точка входа для других модулей.
- Изолированная схема данных: таблицы AuctionResult, AuctionLogs принадлежат только сервису ставок.
- Взаимодействие с другими модулями через публичные интерфейсы (EventFacade, UserFacade).
- ArchUnit-тесты для тестирования границ модулей.
- Для снижения нагрузки на БД и уменьшения блокировок сервиса ставок добавлены асинхронные очереди для событий показов и кликов и перевод тяжёлых запросов на чтение аналитики на реплику.
- Добавлены health-check- и readiness-точки для подготовки к будущему выделению в микросервис.

## Решение на горизонте года

Сервис ставок выделен в отдельный микросервис. Будет предоставлена отдельная ADR.

## Последствия

**Положительные:**

- Быстрая доставка: не нужно строить микросервисную инфраструктуру.
- Чёткие модульные границы снижают риск регрессий.
- Подготовка к эволюции: при необходимости модуль можно выделить в микросервис с минимальными изменениями.

**Отрицательные:**

- Невозможно масштабировать сервис ставок независимо.
- Единая PostgreSQL остаётся «бутылочным горлышком» при экстремальных пиках.
- Команда должна соблюдать дисциплину модульных границ.

**Риски:**

- Если пиковая нагрузка превысит 20 000 RPS, потребуется выделение модуля в микросервис. Оценка разработки — 2–3 недели при наличии чётких интерфейсов.
- Конкуренция за пул подключений к PostgreSQL.
